## Anthropic の MCP プロキシ

Claude Code、claude.ai、Claude Desktop などのプロダクトは、リモート MCP サーバーに直接つなぐのではなく社内のフォワードプロキシを経由しています。プロキシは保存済みトークンの注入、RBAC、内部設定、セキュリティ制御を担っています。

![Anthropic の MCP プロキシのアーキテクチャ](/images/agntcon-2026-mcp-proxy-at-scale/slide-03.png)

この規模で運用していると常に何かしら問題が起きているそうで、そのなかから 3 つに絞った話でした。

1. ユーザーの接続を切らさない（OAuth のリフレッシュ）
2. 上流への無駄なリクエストを減らす（キャッシュ）
3. サーバーの健全性を把握する（エラーの文脈化とログ）

## 1. ユーザーの接続を切らさない

ユーザーの認証は一度きりにしたいので、リフレッシュトークンが要ります。理屈のうえではリフレッシュトークンで新しいアクセストークンを取るだけなのですが、実際にやると 3 か所でつまずく、という話でした。

### そもそもリフレッシュトークンをもらえない

認可サーバーのメタデータに `refresh_token` グラントが載っていれば、リフレッシュ自体はサポートされています。問題は「どうすれば返してくれるか」がサーバーごとに違うことです。

![プロバイダごとに異なる認可 URL のパラメータ](/images/agntcon-2026-mcp-proxy-at-scale/slide-09.png)

| 認可サーバー側の要求 | 例 |
| --- | --- |
| 認可 URL に特定のスコープやパラメータが必要 | `offline_access` スコープ（Entra、Auth0、Okta）、`access_type=offline`（Google）、`token_access_type=offline`（Dropbox）、`duration=permanent`（Reddit） |
| クライアントメタデータの `grant_types` に `refresh_token` の宣言が必要 | 宣言がないと発行しない厳格なサーバーがある |
| プロバイダのコンソールで有効化が必要 | Slack のトークンローテーション、GitHub Apps のトークン有効期限 |
| 何もしなくても常に返す | HubSpot、Asana、Zoom、Box |

Dropbox の `token_access_type=offline` のように、どの仕様にも書かれていないパラメータもあります。これをどうやって知るかというと、ドキュメントを読むか、リフレッシュトークンがいつまでも返ってこないことに気づくかのどちらかだそうです。

登壇者は「LLM クライアントは史上初のユニバーサルな OAuth クライアントで、あらゆるサーバーの癖を吸収することが期待されている」と言っていました。今までは OAuth プロバイダごとに個別のインテグレーションを書くのが普通だったのに、MCP ではどのサーバーにもそのままつながることが期待される。だからプロバイダごとの癖に向き合うしかない、ということです。

### 並行リクエストがトークンを壊す

同じユーザーが複数のクライアントから同じ MCP サーバーを使っていると、トークンの期限切れと同時に複数のリクエストがリフレッシュを試みます。

![並行リフレッシュがトークンを無効化するシーケンス](/images/agntcon-2026-mcp-proxy-at-scale/slide-14.png)

リクエスト A が `R1` でリフレッシュに成功して `R2` を得た直後に、リクエスト B が使用済みの `R1` でリフレッシュを試みます。このとき一部の認可サーバーは、同じリフレッシュトークンの二重利用をトークン盗難の兆候とみなして、`R2` を含むグラント全体を失効させます。ユーザーは何もしていないのに「再接続してください」と言われ、しかもよく使う人ほど確実に踏みます。

対策は Redis の分散ロックでした。

![分散ロックで同時に 1 つのリフレッシュだけを許可する](/images/agntcon-2026-mcp-proxy-at-scale/slide-15.png)

ロックを取ったリクエストだけが認可サーバーに行き、待っている側はロックが空いたらストアを読み直して、新しいトークンがあればそれを使います。10 並行でも認可サーバーへの呼び出しは 1 回です。細かい工夫も 3 つ挙がっていました。有効期間の最後の約 5% で早めにリフレッシュする。待つ側のタイムアウトを「まだ有効なトークンがあるなら数秒」「既に死んでいるならリース期間いっぱい」の 2 種類にする。待つ側は失敗も読んでバックオフする。最後のは自分で書いたら抜かしそうです。

### リフレッシュ失敗が回復できるものか分からない

RFC 6749 では、トークンエンドポイントのエラーは `invalid_grant` や `invalid_client` など 6 種類と決まっています。全サーバーがこれに従っていれば、リトライか再認証かはただの表引きです。

![リフレッシュ失敗の約 25% は OAuth 準拠のエラーではない](/images/agntcon-2026-mcp-proxy-at-scale/slide-19.png)

実際には、Anthropic のデータでリフレッシュ失敗のうち仕様どおりだったのは 74% でした。約 10% は OAuth 形式でない 5xx で、残り 16% はエンドポイントが消えた 404、存在しないエラーコードを返す 401、トークンの入っていない 2xx など雑多なものです。ステータスと形式は正しいのに `error` が `server_error` という、トークンエンドポイントでは定義されていない値だった実例が紹介されていました。リトライすべきかどうかはレスポンスからは分かりません。

方針は 4 つでした。準拠したエラーはそのまま信じる。よく使われるサーバーの非準拠エラーは個別に覚えて、認識したらリトライをやめる。それ以外は一定期間バックオフして諦める。そしてリフレッシュの結果がどうであれ、MCP サーバーが 401 を返すまでトークンを有効とみなす。最後のは、エラー解釈に深入りしすぎないための割り切りだと受け取りました。

## 2. 上流への無駄なリクエストを減らす

最初のプロキシは透過的でした。ツール一覧を求められるたびに `initialize` → `notifications/initialized` → `tools/list` をそのまま上流へ流し、毎回セッションを作り直していました。1 ユーザー・1 サーバーで 4 セッション・12 リクエスト・ツール呼び出し 0 回、という状態です。ダッシュボードで気づいたのではなく、パートナー企業に指摘されて判明したそうです。

![プロキシでの多層キャッシュ](/images/agntcon-2026-mcp-proxy-at-scale/slide-27.png)

セッション ID と `*/list` の結果をユーザー + サーバー単位で 1 時間キャッシュして、1 セッション・3 リクエストまで減らしました。ただログ上の `tools/list` レスポンスのハッシュを比べたところ、約 92% のサーバーは全ユーザーに同じツール一覧を返していました。ユーザー単位のキャッシュは、ほとんど起こらないケースのためにエントリを増やしていただけでした。

![2026-07-28 仕様改訂で追加されたキャッシュ指示](/images/agntcon-2026-mcp-proxy-at-scale/slide-30.png)

これを受けて 2026-07-28 の MCP 仕様改訂で、`tools/list` などのレスポンスに `ttlMs` と `cacheScope` を含められるようになりました。`public` ならサーバー単位、`private` ならユーザー単位でキャッシュしてよい、とサーバーが宣言する形です。同じ改訂でセッションと `initialize` ハンドシェイクもなくなったので、セッションキャッシュは役目を終えることになります。

## 3. サーバーの健全性を把握する

MCP サーバーの失敗は、ネットワーク、HTTP、JSON-RPC エラー（200 だがボディがエラー）、ツール結果の `isError: true` の 4 層で起きます。さらに同じステータスでも文脈で意味が変わります。404 は MCP の文脈では「セッション終了」なので張り直せば済みますが、HTTP の文脈では「エンドポイントがない」なので設定を直すまで動きません。401 も、トークンを送って拒否されたのか、そもそも送れていなかったのかで責任が違います。

そこで Anthropic では、HTTP エラーをそのまま投げるのではなく、文脈込みで `error_code` と `fault`（責任領域）に対応づけています。

![ステータスと文脈から error_code と fault へのマッピング](/images/agntcon-2026-mcp-proxy-at-scale/slide-34.png)

| ステータス | 文脈 | `error_code` | `fault` |
| --- | --- | --- | --- |
| 401 | 保存済みグラントが死んでおりリフレッシュ不能 | `mcp_invalid_oauth_token` | `user_auth_expired` |
| 401 | ユーザーがこのサーバーに接続したことがない | `mcp_unauthorized_no_token` | `expected_noauth` |
| 404 | URL が MCP サーバーではなく Web サイトとして応答 | `mcp_endpoint_not_found` | `misconfiguration` |
| 502 | サーバーがストリーム途中で接続を切った | `mcp_connection_error` | `upstream_server` |
| 500 | 内部で保存済みトークンを取得できなかった | `mcp_token_fetch_failed` | `internal` |
| 429 | 認可サーバーがリフレッシュをレート制限 | `mcp_upstream_auth_rate_limited` | `upstream_auth_server` |

これをリクエストごとに 1 行の構造化ログにしています。判定、使ったクレデンシャルの状態、上流が返したもの、自分たちが返したもの、キャッシュの結果が全部 1 行に入っているので、サーバーごとの状況を 1 つのログから追えます。

![リクエストごとに 1 つの構造化ログ](/images/agntcon-2026-mcp-proxy-at-scale/slide-35.png)

一方で、この可視性をサーバー開発者に共有することはまだできていないそうです。「もしプロキシをゼロから作るなら、これを最初に入れる」と何度か言っていました。

## 締めのメッセージ

認可サーバーを作る人へは 2 点でした。DCR ではなく CIMD（Client ID Metadata Document）か事前登録クライアントを使ってほしい。DCR だと自分が作っておらず連絡もできないクライアントのデータベースを抱えることになり、登録が消えるとクライアント側には `invalid_client` しか見えません。もうひとつは、OAuth 準拠のエラーを文字どおりの意味で使ってほしい。`invalid_grant` はグラントが本当に死んだときだけ使い、ダウンしているなら `Retry-After` 付きの 503 や 429 でそう言ってほしい、という訴えでした。

![今日 MCP プロキシを作るならやること](/images/agntcon-2026-mcp-proxy-at-scale/slide-38.png)

今プロキシを作るなら、というリストも示されました。リフレッシュを分散ロックの背後でやる。新仕様のキャッシュを使う。1 リクエスト 1 行の構造化ログと、責任領域つきのエラーコードを持つ。サーバーの健全性を初日からサーバー開発者に見せる。時間切れで話せなかった点として、サーバーごとの認可サーバーメタデータの上書きと、認可ディスカバリのキャッシュも挙がっていました。

## 感想

MCPass では AgentCore Identity の OAuth フローが一部の SaaS で動かず、認証情報管理を自前実装に切り替えました。当時は AgentCore 側の互換性の問題だと片づけていたのですが、あらゆる認可サーバーの癖を吸収するという要件自体が MCP 以前にはなかったものです。どのマネージドサービスを使っても、最後は自分たちで癖を潰すことになります。プロバイダごとのパラメータを設定として持てる作りにしておくべきでした。

分散ロックは規模に関係なく起きる問題です。社内でも 1 人が Claude Code と IDE 拡張とチャット UI を同時に開くのは普通で、よく使う人から順に「再接続してください」が出るのは、推進する側としてかなり嫌な出方です。MCPass の認証情報管理の優先度を上げることにしました。

キャッシュについては、MCPass では Tool Discovery を自前で持っていて、ユーザーごとに見せるツールをフィルタリングしています。上流からは `cacheScope: "public"` のツール一覧を受け取っておいて、ゲートウェイ側で RBAC をかける、という整理になりそうです。セッションと `initialize` ハンドシェイクの廃止は、セッション ID をキーにした監査ログやレート制限を持っている実装には小さくない変更です。

構造化ログの `fault` は、MCPass の監査ログに足りていないものでした。今は誰がいつどのツールを呼んだかの記録が中心で、失敗したときにゲートウェイの障害か・接続先 SaaS の障害か・ユーザーの再認証待ちか・管理者の設定ミスかがログの時点で分かれていません。ここが分かれていれば「AI が動かない」という問い合わせの一次切り分けがかなり楽になります。
